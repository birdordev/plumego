### PostgreSQL 同步备库提升演练

在仓库根目录运行 `make cloud-manager-console`。使用支持 Unix 套接字的非 root 环境，将同一 PostgreSQL 主版本的 `initdb`、`pg_ctl` 和 `pg_basebackup` 加入 PATH。在云管模块运行以下命令。

```sh
CLOUD_MANAGER_TEST_FAILOVER=1 go test -race -count=1 -timeout=120s \
  ./cmd/cloud-manager -run '^TestAcceptanceCloudManagerDatabaseFailover$' -v
```

演练启用同步流复制和 `remote_apply`。用腾讯云签名 TLS 夹具制造已确认开机和已在远端生效、仍等回执的关机。旧主停止且原连接失效后才提升备库。使用同一 API 服务与包含两个节点的读写连接池，记录就绪恢复时间，并核对已确认操作 ID、事件投递 ID 和在途租约。演练加速租约过期，验证新的只读 Worker 领取后旧持有者无法确认，迟到的旧执行者也无法覆盖结果，并单独记录只读结算耗时。[PostgreSQL 同步复制](https://www.postgresql.org/docs/current/warm-standby.html)

现场验收须验证实际仲裁、带外隔离、连接端点或服务发现、复制延迟、旧主重新加入、厂商写入边界，以及部署的恢复时间和数据丢失指标。

### PostgreSQL 时间点恢复演练

在仓库根目录运行 `make cloud-manager-console`。使用支持 Unix 套接字的非 root 环境，将同一 PostgreSQL 主版本的 `initdb`、`pg_ctl` 和 `pg_basebackup` 加入 PATH。进入云管模块后运行以下命令。演练只连接自行创建的临时 PostgreSQL 集群，远端状态由本地签名 TLS 夹具保存。

```sh
CLOUD_MANAGER_TEST_PITR=1 go test -race -count=1 -timeout=120s \
  ./cmd/cloud-manager -run '^TestAcceptanceCloudManagerPointInTimeRecovery$' -v
```

演练使用物理基础备份和归档 WAL 恢复至命名标记。标记前已有一次启动成功，另一次关机在远端生效且本地仍持有派发租约，同时留有一项未派发的启动。标记后提交的另一项请求和原关机的后续终态都进入归档。恢复前停止源 Worker 和数据库。恢复后沿用可写的厂商配置，以 `observe-only` 启动 Worker。关机须通过只读观测结算，远端写入次数保持两次，且排序更靠前的未派发任务仍为 `queued`、尝试次数为零。AWS 创建的自动重发冻结由 `TestAcceptancePersistentInstanceCreation` 验证。[PostgreSQL 归档与时间点恢复](https://www.postgresql.org/docs/current/continuous-archiving.html)

源端结算后，发布器将两条成功事件送达独立的 PostgreSQL 接收库。恢复后的发布器重送原启动事件，并发送重新生成的关机事件。接收端验证 HMAC，检查前者的投递 ID 和正文摘要，后者使用新的投递 ID 以及原有效果标识。两条时间线合计应留下三条投递回执和两条业务效果记录。

在恢复库启动发布器前，读取独立接收库持久化的终态回执。云端只读观测前，对账应将原启动标为 `matched`、关机标为 `source_unsettled`。只读结算后对账应报告一个 `matched` 和一个 `regenerated`。CLI 验收还覆盖缺失操作、跨项目隔离、摘要冲突和已结算但缺少发件箱记录。

为接收端导出声明完整的 `coverage` 窗口后，核对另一侧的缺失回执。CLI 验收覆盖同一时刻的不同终态、窗口起止、本地四种投递状态、时间冲突、重新生成的投递、跨项目空清单，以及过大窗口拒绝。

目标环境验收还需核对存储和归档连续性、旧实例隔离、恢复点之后有无未入账的云端效果、对外发件箱接收方状态，以及实际 RTO 和 RPO。

### API 滚动升级与回退演练

在基线和候选各自的源码根目录运行 `make cloud-manager-console`，再各自执行 `go -C reference/with-cloud-manager build -o "$ROLLOUT_BINARY" ./cmd/cloud-manager`。为两次构建分别指定不同的输出路径，记录源码版本、构建配置和产物 SHA-256。使用非 root 环境，并将同版本 PostgreSQL 的 `initdb`、`pg_ctl` 和 `pg_basebackup` 加入 PATH。进入候选源码的云管模块后运行。

```sh
CLOUD_MANAGER_TEST_ROLLOUT_BASELINE=/absolute/path/baseline/cloud-manager \
CLOUD_MANAGER_TEST_ROLLOUT_CANDIDATE=/absolute/path/candidate/cloud-manager \
  go test -race -count=2 -timeout=120s -v ./cmd/cloud-manager \
  -run '^TestAcceptanceCloudManagerAPIRolloutAndRollback$'
```

基线进程先迁移和受理，再与候选进程共用同一临时 PostgreSQL。候选启动后先通过存活探测，在迁移前返回未就绪。候选迁移期间持续探测基线就绪及操作读取，再核对两版 API 同时可用。候选用原幂等键读取基线的待执行请求，校验原操作 ID、目标、动作、状态和受理时间。随后候选受理新的操作，基线读取其结果。停止候选并在同一监听地址启动基线，保留候选的数据库迁移。

核对两个版本的操作时间线、管理员审计及项目隔离。比较已有终态事件的投递 ID 和原始正文，候选迁移后生成的终态在回退后保留原效果标识。候选留下一项已到期的开机请求，基线 API 用原幂等键找回同一操作，随后由回退后的 Worker 结算。三次预期写入各发生一次。一项到期时间更晚的基线请求贯穿演练并保留零尝试次数。

常规测试使用进程内 Worker 和腾讯云 TLS 夹具。在 Linux 上为同一命令额外设置 `CLOUD_MANAGER_TEST_ROLLOUT_PROCESS_WORKERS=1`，并将 `-timeout` 调整为 `150s`。该模式启动基线和候选各自的 `worker` 子命令，分别在腾讯云、阿里云和华为云协议夹具上执行。启动基线 Worker 之前，先让候选的 `observe-only` Worker 完成一次 PostgreSQL 队列轮询并退出，再检查已到期的未派发操作仍处于排队状态且尝试次数为零。

独立进程模式也演练启用放量策略后的回退。候选先设置白名单、受理一笔操作，再冻结策略并关闭账号写入。基线 API 拒绝新申请，基线 Worker 将原排队任务结算为失败，厂商写入计数保持不变。恢复候选后，先验证空策略继续拒绝新申请，再逐项放行并核对旧操作回执未复活，新请求只产生一次厂商效果。

独立进程模式使用临时 CA，证书信任限定在各 Worker 子进程。测试 HTTPS 代理仅接受当前夹具的厂商主机名，并始终连接同一回环 TLS 监听器。在容器中复跑时，可用 `go test -c` 构建与容器架构一致的测试程序，将它与两个产物放入带 PostgreSQL 工具的 Linux 容器，以非 root 用户在 `--network none` 下运行测试。

目标环境使用拟上线和可回退版本复跑，并核对真实流量切换、实际 Worker 副本的排空和接续、下游接收方对事件字段的兼容，以及批准账号的逐档放量和写入冻结。

队列租户索引的在线迁移单独验证。保持一个持有队列表写入锁的事务，让索引创建进入等待阶段。在等待期间通过既有 API 受理开机，观察共享 Worker 领取、写入和结算，核对厂商夹具仅接到一次派发。中断后校验迁移未记账及首个索引无效。释放等待事务后同时运行两个迁移实例，确认修复后两个索引可用，只有一条完成记录，并用原幂等键找回同一操作。目标环境另测较大队列及长事务下的构建时长、CPU、I/O 和受理尾延迟。

### 目标环境操作时延验收

使用目标环境的只读项目凭据，对每个已批准的厂商、账号、地域和动作声明门槛。以下为单项示例，同一窗口内可列出最多 32 个不同的账号、地域和动作组合。阈值按实际放量档案填写。

```json
{
  "version": 1,
  "tenant": "lab",
  "project": "compute",
  "from": "2026-11-28T08:00:00Z",
  "until": "2026-11-28T08:15:00Z",
  "cases": [
    {
      "name": "tencent-start",
      "provider": "tencent-cvm",
      "account": "tencent-lab",
      "region": "ap-guangzhou",
      "action": "start",
      "minimum_accepted": 100,
      "minimum_success_bps": 9900,
      "maximum_pending": 0,
      "maximum_needs_review": 0,
      "queue": {"minimum_coverage_bps": 10000, "maximum_p95_ms": 30000},
      "convergence": {"minimum_coverage_bps": 10000, "maximum_p95_ms": 120000}
    }
  ]
}
```

```sh
cloud-manager operations verify-latency lab compute < acceptance.json > operation-acceptance.json
```

每项查询使用同一受理窗口和精确作用域，报告保存各次数据库观测时间。观测时间应达到窗口结束，API 回显须匹配清单和厂商。成功率以受理数为分母，首次领取样本覆盖以已入队数为分母，自动收敛样本覆盖以成功数为分母。比率门槛用基点表示，`10000` 代表 100%。无可核对样本时覆盖检查失败。需要单独限制未完成或待复核操作时，填写 `maximum_pending` 和 `maximum_needs_review`。

报告归档清单去除首尾空白后的 SHA-256、每项门槛、有效快照及原因。任何门槛失败、作用域不一致、窗口未结束或查询出错均返回非零状态，同一项目中的其他用例仍会完成检查。退出成功且 `threshold_met` 为 `true` 时，归档报告、批准清单、候选版本及同一负载窗口的厂商副作用对账和回退记录。

### 目标环境盘点采样

按批准的账号、地域和资源类型清单核对启用计划，分别为腾讯云、阿里云和华为云运行 `governance inventory-sample --scope-manifest`。留存批准清单和 NDJSON，归档版本、环境、账号作用域和发布负载。检查命令成功退出且末行 `threshold_met` 为 `true`，确认每个样本的范围指纹与预期一致。调度状态和就绪逾期提供每次观测的积压证据，采样间隔内的变化需要结合运行指标核对。

在同一测试窗口为全部普通盘点控制器启用 `CLOUD_MANAGER_CONTROLLER_DISPATCH_LOG=1`。将同一部署、同一数据库历史的副本标准输出提取为逐行原始 JSON 对象，允许乱序和重复采集。按部署批准的窗口、低流量租户及等待门槛运行，以下参数为示例。

```sh
cloud-manager governance inventory-dispatch-stats \
  --from 2026-11-28T08:00:00Z --until 2026-11-28T08:15:00Z \
  --expect lab/tencent-cvm --expect lab/alibaba-ecs --expect lab/huawei-ecs \
  --expect quiet/tencent-cvm --max-p95-ms 120000 \
  < controller.ndjson > dispatch-stats.json
```

命令离线读取日志，无须数据库连接、API 地址或令牌。窗口按数据库 `claimed_at` 取左闭右开区间，按 `(schedule_id, fence)` 去重。报告包含输入 SHA-256、重复数，以及按厂商、租户和租户／厂商组合汇总的领取数、最近秩 p50、p95 和最大等待毫秒。`--expect` 可重复，声明应有领取的组合。`--max-p95-ms` 可选，按每个有领取的组合检查。窗口没有领取、预期组合缺失或 p95 超限时会输出 `threshold_met: false` 并以非零状态退出。日志损坏、领取内容冲突或窗口超过 25 万条唯一领取时退出并省略报告。

归档原始日志、窗口参数和报告。按厂商退避发生的时段重跑同一命令。使用盘点采样和调度积压核对仍未领取的到期范围，并用各副本采集状态核对退出、重启和丢失区间。领取统计只覆盖成功采集的领取事件。

### 目标环境资产查询验收

在已批准的目标环境准备资产清单和只读项目令牌。将 `CLOUD_MANAGER_API_URL`、`CLOUD_MANAGER_API_TOKEN` 指向该环境。按实际资产和授权编写负载文件，至少覆盖首页、账号筛选、可辨识的稀有命中，以及预期空结果。测试共享场景时，在对应查询的 `allowed_projects` 显式列出允许返回的归属项目。以下示例采用每秒 200 次、30 秒和 250 毫秒的初始门槛，账号、地域、资产 ID、关键词及期望条数须换成目标环境的值。

```json
{
  "tenant": "lab",
  "project": "compute",
  "requests_per_second": 200,
  "duration_seconds": 30,
  "workers": 16,
  "maximum_p95_ms": 250,
  "cases": [
    {"name":"first","kind":"instance","limit":50,"expected_items":50},
    {"name":"account","kind":"instance","account":"sandbox-1","limit":50,"expected_items":50},
    {"name":"rare","kind":"instance","q":"capacity-sentinel","limit":50,"expected_items":1,
     "required_asset":{"project":"compute","account":"sandbox-1","region":"ap-guangzhou","id":"ins-sentinel"}},
    {"name":"empty","kind":"instance","q":"private-project-sentinel","limit":50,"expected_items":0}
  ]
}
```

```sh
cloud-manager governance asset-capacity lab compute < workload.json > asset-capacity.json
```

每条查询先验证一次返回合同，预检失败时输出失败报告，不进入正式测量。测量轮转各查询，从计划到达时刻开始计时，包含排队、传输和响应校验。执行槽位、排队数量和每次请求从计划时刻起的 10 秒期限均有上限。报告逐条记录计划数、成功数、失败数、丢弃数及成功响应的 p95。任何失败、丢弃或单条查询超出 p95 门槛都会使 `threshold_met` 为 `false`，命令以非零状态退出。报告记录用例名称和检查结果。清单去除首尾空白后计算 SHA-256，报告省略查询参数和资产内容。

归档负载清单、命令结果、候选版本、部署环境及同一窗口的盘点压力。分别记录空闲和实际盘点写入时的结果，并用现场资产范围与清单中的正负用例核对租户隔离。

在负载清单顶层加入 `inventory` 可联合验收查询容量与多云盘点。`scopes` 必须列出参与验收的每个厂商在该项目内全部启用的普通盘点范围。以下为三家云各含一个范围的示例。`sample_interval_seconds` 默认 5 秒，支持 1 至 60 秒，每份清单最多包含 8 个厂商。

```json
{
  "inventory": {
    "sample_interval_seconds": 5,
    "scopes": [
      {"provider":"tencent-cvm","account":"tencent-lab","region":"ap-guangzhou","kind":"instance"},
      {"provider":"alibaba-ecs","account":"alibaba-lab","region":"cn-hangzhou","kind":"instance"},
      {"provider":"huawei-ecs","account":"huawei-lab","region":"cn-north-4","kind":"instance"}
    ]
  }
}
```

同一次命令在相同项目 API 上按厂商分组采样。`before` 基线通过后启动负载，记录 `during` 样本，负载结束后再取 `after` 样本。每轮必须满足每个厂商的范围总数、范围指纹和 900 秒窗口内至少 95% 新鲜三项要求。相同数量和新鲜度的范围替换也会使验收失败。报告中的 `inventory.rounds` 留存采样时段、预期与观测指纹、调度积压和失败原因。任一采样或查询不达标，整体退出状态为非零。单独的 `inventory-sample` 继续用于更长窗口的盘点趋势和调度验收。

### 项目资产查询基准

将 `CLOUD_MANAGER_TEST_DATABASE_URL` 指向允许创建临时 schema 的 PostgreSQL 测试数据库。构建控制台资源后，在云管模块运行基准。

```sh
go test ./cmd/cloud-manager -run '^$' -bench '^BenchmarkProjectAssets$' -benchtime=96x -cpu=4 -count=1
```

基准生成三家优先厂商共 50 个云账号，每账号 4 个地域，每地域 500 条实例资产。8 路请求混合查询普通首页、指定账号、稀有关键词和零匹配。基准检查 HTTP 状态和返回行数，分别记录四类请求的 p95 和总吞吐。

使用同一数据集运行 30 秒固定到达率验收。

```sh
CLOUD_MANAGER_TEST_ASSET_TARGET_RATE=1 go test ./cmd/cloud-manager \
  -run '^TestCapacityProjectAssetsAtTargetRate$' -cpu=4 -count=1 -v
```

每 5 毫秒安排一个请求，共 6,000 个。负载发生器使用 16 个执行槽位，排队上限为 250 毫秒的计划请求数减去执行槽位，共 34 个。队列满计为丢弃。延迟从计划时刻开始计算，包含排队时间。验收要求全部请求成功、四类查询的 p95 均不超过 250 毫秒，且三家厂商的 200 个盘点范围通过联合采样。目标环境放行还需覆盖实际授权分布、资源类型及盘点写入竞争。

使用同一固定到达率验证查询与盘点并行。

```sh
CLOUD_MANAGER_TEST_ASSET_TARGET_RATE=1 go test ./cmd/cloud-manager \
  -run '^TestCapacityProjectAssetsWithInventoryWrites$' -cpu=4 -count=1 -v
```

主租户包含共享与私有云账号，第二个租户包含同名账号和实例。查询增加共享及私有账号两组，稀有关键词在三个授权域中各有一条记录，用于检验只返回项目可见的实例。四个普通调度循环驱动 204 个范围，每个范围通过两页本地发现并实际提交 PostgreSQL。验收要求六类读取 p95 均不超过 250 毫秒且 6,000 次读取全部成功，并在 30 秒窗口内完成至少 95% 的范围。每个完成范围校验凭据代次、两页共 500 个资产和 100 个状态更新。真实远端响应时间及限流另在厂商沙箱取样。
