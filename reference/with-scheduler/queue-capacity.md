# PostgreSQL 领取与过期清理验证

测量环境为本机 PostgreSQL 18.4、Go 1.26.0 和 macOS arm64。各测试使用独立 schema。用临时或专用 PostgreSQL 实例复现。

```sh
PLUMEGO_TEST_QUEUE_CAPACITY=1 go -C reference/with-scheduler test -count=1 -v -timeout 180s \
  -run '^TestPostgres(QueueClaimPlans|QueueExpiryLatency|BoundedExpiryAndStableClaims)$' ./...
```

测试从 `PLUMEGO_TEST_POSTGRES_DSN` 读取连接信息。

## 过期积压

每轮重建 2,000 条其他 Topic 的过期任务和一条目标 Topic 的可运行任务。交错测试两种领取方式，各采样 100 次。耗时从调用方计时，包含数据库往返与事务提交。独立清理批次处理 128 条记录。

| 操作 | p50 | p99 |
|---|---:|---:|
| 领取事务内清理全部过期任务后领取 | 81.61 ms | 117.50 ms |
| 独立清理配置下领取 | 2.93 ms | 17.37 ms |
| 独立清理事务，每批 128 条 | 4.84 ms | 6.11 ms |

锁冲突用例在另一 Topic 持有过期记录的行锁，原领取路径等待至 120 ms 的测试期限。独立清理配置下，可运行任务成功领取，清理跳过被锁记录和有效租约。独立清理进程测试还验证了过期状态与租户待处理额度在同一提交中更新。

## 领取执行计划

数据集共 104,128 行，包含 60,000 条已完成历史、20,000 条未来任务、10,000 条其他 Topic 待领任务、10,000 条其他 Topic 可接管租约和 4,000 条有效租约。目标 Topic 各有 64 条待领和租约到期记录。表中取 `EXPLAIN (ANALYZE, BUFFERS)` 候选扫描节点的估算、实际输出和过滤行数，最终查询限制为 32 条。

| 候选分支 | 索引 | 估算输出 | 实际输出 | 扫描后过滤 |
|---|---|---:|---:|---:|
| 待领 | `mq_tasks_ready` | 19,580 | 64 | 0 |
| 单独探测租约到期 | `mq_tasks_lease_expiry` | 891 | 64 | 10,000 |
| 合并领取 | `mq_tasks_ready`、`mq_tasks_reclaim_topic` | 20,214 | 128 | 0 |

合并领取使用两个索引生成位图，估算偏高时仍只读取符合 Topic 和时间范围的 128 条候选。独立租约谓词探测可能选择全局租约索引，检查更多其他 Topic 的候选。相同优先级和创建时间按任务 ID 排序，已锁定的合格记录会跳过，释放行锁后可重新领取。测量适用于上述数据和本机负载。

## 空队列轮询与提交延迟

```sh
PLUMEGO_TEST_QUEUE_CAPACITY=1 go -C reference/with-scheduler test -count=1 -v -timeout 70s \
  -run '^TestPostgresQueuePollingProbe$' ./...
```

空队列查询量在四个 Worker 预热后采样两秒，计入领取查询和最早可见时间查询。事务控制命令及通知会话的初始化单独运行。延迟由一个 Worker 测量，从提交开始到处理器启动，各采样 60 个任务。自适应模式在延迟实验中使用专用 PostgreSQL 通知连接。

| 模式 | 空队列查询／秒 | 提交到处理器 p50 | 提交到处理器 p95 |
|---|---:|---:|---:|
| 固定 20 ms 周期 | 184.9 | 23.22 ms | 26.53 ms |
| 自适应 20–400 ms，带抖动与通知 | 23.0 | 2.44 ms | 5.88 ms |

另有测试验证事务提交后才通知、回滚丢弃通知、监听会话被终止后重连，以及完全没有通知时仍按可见时间或周期探测领取。参考进程的空闲配置为 200 ms 至 2 s，表中使用较短间隔缩短本机采样时间。

## 批量提交与 ACK

```sh
PLUMEGO_TEST_QUEUE_CAPACITY=1 go -C reference/with-scheduler test -count=1 -v -timeout 90s \
  -run '^TestPostgresQueueBatchProbe$' ./...
```

每组 32 条同租户短任务，每种模式测 32 组，共 1,024 条。提交阶段计入应用仓储和事务，ACK 阶段计入 SQL 写入与事务，两者均包含各自触发器。领取和处理器执行不计入表中时间。WAL 数值取隔离 PostgreSQL 实例上的插入位置增量。

| 操作 | 条／秒 | 整组 p95 | WAL 总字节 | WAL 字节／条 |
|---|---:|---:|---:|---:|
| 逐条提交 | 1,565.4 | 32.41 ms | 1,567,632 | 1,530.9 |
| 批量提交 | 9,753.9 | 5.12 ms | 1,536,016 | 1,500.0 |
| 逐条 ACK | 3,535.7 | 12.97 ms | 436,800 | 426.6 |
| 合并 ACK | 13,329.5 | 4.01 ms | 530,800 | 518.4 |

合并 ACK 提高了该样本的吞吐量，每条 WAL 字节约增加 22%。该探测直接测 SQL 批量入口，参考 Worker 以两毫秒收集实际并发完成的任务。等待窗口、业务耗时和实际批量大小会影响端到端结果。

约束注入验证提交失败时，新任务、审计行和额度一起回滚，调用方用原幂等键重试。ACK 写入失败时，整组保留领取状态。更新成功时，旧领取代次仅影响自身返回结果，同组的有效领取可以完成。
