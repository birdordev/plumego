# 调度容量基线

使用同一个本地夹具运行工作负载和同步备库切换。需要可用的 Go、Python 3.8+、PostgreSQL Server 与客户端工具，以及 POSIX 的 `ps`。脚本在临时目录启动数据库、只监听回环地址，测试完清理进程和数据。

```sh
PYTHONDONTWRITEBYTECODE=1 GOMAXPROCS=4 \
  python3 reference/with-scheduler/load_baseline.py > baseline.json
```

默认配置为两个调度进程、两个 API、两个短任务 Worker 共八槽、两个 I/O Worker 共四槽及独立终态核对进程。短任务按每秒 240 条提交约 5 秒。长任务为 64 条 250 毫秒 I/O；定时场景将 128 条计划对齐至同一时刻；热点租户一次提交 320 条，另一租户以 40 条／秒提交 32 条；重试场景对 128 条任务各注入一次真实事务失败。切换场景独立运行同步主备，旧主停止时保有 64 条已确认的积压。

## 计量口径

- 吞吐按确认完成的任务计数。持续短任务额外报告提交窗口内的完成速率，定时风暴的总耗时包含约一秒的预留触发时间。
- p99 从计划或入队到终态确认。JSON 另记录物化、排队、执行至回执和回执至确认的 p99。重试任务的执行至回执耗时包含退避与后续尝试。
- 可运行及在途峰值按约 50 毫秒加采样开销的间隔观察。短于一个采样窗口的峰值可能漏记。定时任务在物化前计入创建延迟。
- CPU 按运行期间各 PID 的累计量差值计算。RSS 按采样时把服务或 PostgreSQL 进程的驻留内存相加，共享页面可能重复计数。数据库大小增量报告文件占用变化。WAL 以实例的插入位置差计算，包含同一场景期间的维护活动。
- PostgreSQL 等待事件记录观察次数，用于定位活跃 SQL 可能等待的资源。采样包含实例内的全部服务，次数不能换算为等待时间。
- 切换报告区分 API 恢复与全部对账完成，另外检查确认任务丢失、积压清空、Outbox 重投与实际副作用次数。WAL 覆盖该夹具的故障与恢复窗口。

以下为单机参考数据。容量上限、峰值流量和适用 SLO 需要在目标部署环境以相同口径复测。

## 瓶颈

- **短任务**。领取前等待 p99 为 123.41 ms。活跃 SQL 采样观察到 11 次 `LWLock:WALWrite` 和一次 `IO:WalWrite`。加大目标提交量时，优先看确认批大小、WAL 同步与数据库连接。
- **长 I/O**。四个槽对应的简化上界是每秒 16 条，实测约 14.14 条。排队 p99 为 4.09 秒，处理至回执 p99 为 266.50 ms，观察到 135 次夹具内的 `PgSleep`。主要约束是 I/O 槽位与任务耗时。
- **同刻触发**。计划时间至物化 p99 为 362.25 ms，物化后至执行 p99 为 13.42 ms。需要降低这类尾延迟时，先对比分片物化与错峰配置。
- **热点租户**。高量租户 p99 为 1.73 秒，低量租户也达到 1.68 秒。PostgreSQL CPU 为 3.80 秒，应用为 0.64 秒，采样只观察到一次事务 ID 锁等待。这组数据支持继续测试租户公平分派和数据库写入压力，尚不足以定位特定锁。
- **重试风暴**。每条任务恰好重试一次，第一次开工到回执的 p99 为 1.28 秒。用这组曲线比较重试退避、抖动和预算的调整效果。
- **主备切换**。服务在 0.532 秒恢复就绪，全部对账约 10.34 秒。夹具要求 Outbox 由新持有者重投，完整恢复窗口包含其租约到期等待。
